# 与 DeepSeek 的三轮协作分析纪要

测试期间将实测数据同步给 DeepSeek（深度思考+联网搜索模式）做交叉分析，记录如下。
**原则：DS 的预测以本地实测为准，证伪处均已标注。**

## 第一轮：显存上限分析

**提交**：完整 fp32 测试数据（VAE 矩阵 24/25、采样探针、bf16 计划）+ 4 个问题。

DS 关键论点与验证结果：

| DS 论点 | 实测验证 |
|---|---|
| "采样 6.65G + VAE 2.7G = 9.35G 压线，两阶段可能重叠" | ❌ 证伪。ComfyUI 采样与解码两阶段不重叠，832×480@81帧、720P@81帧全部通过 |
| "832×480@49帧 需实测；720P@33帧 风险较高" | ✅ 通过（6.61G / 6.58G） |
| "0.5s 轮询会漏峰" | ✅ 确认。改 0.1s sysfs 直读后，480P@33帧峰值从 6.65G 修正为 8.2G |
| "零值 latent 与真实 latent 解码显存可能有差异" | ⚪ 基本无影响（conv 分配只看 shape）；真实 latent 计时跑峰值与零值一致 |
| 建议 `--disable-smart-memory` / `--cache-none` | ❌ 不采纳：以 10-30% 速度换稳定，与"性能挖掘"目标相反；20+ 连续测试无碎片累积证据 |
| 建议 bf16 VAE A/B | ✅ 采纳并实测（见第二轮） |

## 第二轮：bf16 与注意力模式

**提交**：bf16 真实 A/B 数据（含一次测试事故的自首：上一轮"bf16 数据"实际误跑在未杀干净的 fp32 服务器上）。

| DS 论点 | 实测验证 |
|---|---|
| "bf16 下 512px tile 有较大概率通过" | ❌ 证伪。fp32/bf16 下 512px 全 OOM；256px/时序32 可过（4.92G） |
| "bf16 提速解码" | ❌ 证伪。gfx1031 MIOpen 卷积路径 bf16 不提速反而慢 60%；bf16 的价值是激活减半 |
| "tiledvaelite 比官方 tiled 更省显存" | ❌ 证伪。同规模 192.7s/7.26G vs 官方 184.6s/4.92G，官方胜 |
| "阶梯里连续 OOM 会污染后续测试" | ✅ 确认（碎片假 OOM 复现，重启后通过） |
| torch.compile 值得试吗 | ⚪ 判定"收益有限+有坑"（需 Triton 且版本不匹配 torch 2.5.1），未投入 |

## 第三轮：扩像素 + 延长时间方案

**提交**：本地约束（10G/20G 磁盘/无 ffmpeg/无 VHS/WanVideoWrapper 已装）+ 网搜结论 + 候选管线。

DS 关键输出（P0-P3 优先级）：

- **A1 直接 121 帧**：✅ 实测通过（8.52G）。上限 ~121 帧（社区：超出后"回弹"首帧）
- **A2 尾帧链式 I2V**：✅ 核心节点实测通过（9.3G，衔接自然、尾部无噪声）。DS 提示 kijai wrapper 的 `WanVideoAddExtraLatent` 有"末4帧噪声"坑 → 稳妥做法：每段多生成 3-4 帧裁掉；进阶可装 VideoChunkTools 做 latent 空间拼接
- **B 扩像素**：生成时直接 720P（已实测）为主；**FlashVSR**（本地已装节点，官方支持 Wan2.2 VAE，8G 档 tiny-long+fp16）为进阶——⚠️ 需先下载 ~3G 模型并做最小验证（有 BF16 张量不匹配的社区报错记录，gfx1031 兼容性未知）；Real-ESRGAN 为保底（ROCm "buggy"）；**SeedVR2 需 12G+ 排除**
- **C/D 补帧合成**：RIFE（12MB）+ PyAV 脚本可替代 VHS，零重依赖
- **观察项**：NVlabs/LongLive（Wan2.2 5B 长视频蒸馏框架，但 NVIDIA 导向，ROCm 无文档）

## 方法论沉淀

1. AI 交叉分析适合做"假设生成器"，**每个假设都必须回到本地实测**——本轮 DS 的 5 个可验证预测中 3 个被证伪
2. 测试基础设施要点：阶梯自适应重试、0.1s sysfs 峰值监控、输出逐帧亮度/NaN 统计、换种子击穿节点缓存以分离各阶段耗时
3. 服务器切换必须验证端口归属（`ss -ltn`），避免"测了个寂寞"
